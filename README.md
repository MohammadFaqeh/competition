# منصة المسابقة السنوية القرآنية

تطبيق ويب بملفات ثابتة (بلا خطوة بناء) لإدارة مسابقة سنوية لتحفيظ القرآن الكريم: تسجيل المتسابقين، سحب مواضع الاختبار بعدالة تامة، التقييم الإلكتروني للجان، وتصدير النتائج.

## طريقتا العمل

| | فرع الكورة (سحابي) | استخدام محلي (أي فرع آخر) |
|---|---|---|
| مكان حفظ البيانات | Supabase (مشتركة بين كل الأجهزة) | هذا الجهاز فقط (localStorage) |
| الأدوار المتاحة | مدير، أدمن فرعي، رئيس/عضو لجنة | مشرف واحد فقط |
| يحتاج إنترنت | نعم (للمزامنة، ليس للسحب نفسه) | لا |

يختار المستخدم الطريقة من الشاشة الأولى (`gatewayScreen`)، ولا تُرسل بيانات "الاستخدام المحلي" لأي خادم إطلاقاً.

## الأدوار

- **المدير (Admin):** حساب Supabase Auth واحد. يدير المتسابقين، اللجان، حسابات الأدمن الفرعي، ويعتمد كل الإعدادات.
- **الأدمن الفرعي (Sub-admin):** حساب برمز دخول + PIN، مقيّد بجنس واحد (ذكور أو إناث) فقط، لا يدير اللجان ولا يحذف الجميع.
- **رئيس لجنة الاختبار:** يبدأ الاختبار، يرصد الأخطاء، يقارن رصده برصد العضو، ويعتمد النتيجة النهائية.
- **عضو لجنة الاختبار:** يرصد الأخطاء بشكل مستقل عن الرئيس؛ رصده يُرسل للرئيس للمقارنة ولا يعتمد النتيجة بنفسه.

كل الأدوار السحابية تسجّل الدخول برمز + PIN (لا بريد إلكتروني)، عدا المدير الذي يدخل ببريد وكلمة مرور عبر Supabase Auth.

## البدء السريع (محلي)

المشروع ملفات ثابتة بالكامل، يكفي أي خادم HTTP بسيط لتشغيله محلياً (لا يعمل بفتح `index.html` مباشرة بمتصفح بسبب طلبات `fetch`):

```bash
npx serve .
# أو
python -m http.server 8000
```

ثم افتح `http://localhost:<port>` واختر "بدء الاستخدام المحلي" لتجربة النظام فوراً بلا أي إعداد Supabase.

## تجهيز فرع الكورة (Supabase)

1. أنشئ مشروع Supabase جديداً، وفعّل امتداد `pgcrypto`.
2. نفّذ ملفات `supabase/*.sql` من SQL Editor **بهذا الترتيب بالضبط** (كل ملف يعتمد على سابقه):

   1. `schema.sql`
   2. `committee-pin-migration.sql`
   3. `exam-readiness-hardening.sql`
   4. `committee-live-draw.sql`
   5. `two-examiners.sql`
   6. `sub-admins-and-committee-upgrade.sql`
   7. `sub-admin-committee-assignment-visibility.sql`
   8. `security-fix-null-safe-admin-checks.sql`
   9. `login-rate-limit-and-audit.sql`
   10. `admin-safe-state-merge.sql`
   11. `participant-transfer.sql`
   12. `committee-force-delete.sql`
   13. `supervisor-role.sql`
   14. `committee-claim-transferred-level.sql`
   15. `committee-self-draw-permission.sql`

3. انسخ `supabase-config.example.js` إلى `supabase-config.js`، وضع فيه **Project URL** ومفتاح **anon** العام فقط من إعدادات المشروع.
   لا تضع مفتاح `service_role` في أي ملف داخل الموقع — هذا المفتاح يمنح صلاحيات كاملة ويجب أن يبقى خارج أي كود يصل للمتصفح.
4. أنشئ أول حساب مدير: أضف مستخدماً من Supabase Auth، ثم أدرج له صفاً في جدول `profiles` بـ `role='admin'`.
5. من إعدادات الموقع (بعد الدخول كمدير) أنشئ اللجان وحسابات الأدمن الفرعي.

الأمان مبني بالكامل على صلاحيات قاعدة البيانات (Row Level Security + دوال `SECURITY DEFINER`)، لا على منطق الواجهة — مفتاح `anon` العام مكشوف بالضرورة في كود الموقع، ولا يملك أي وصول مباشر للجداول، فقط تنفيذ دوال محدَّدة يتحقق كل واحد منها من الصلاحية داخلياً.

بعد تنفيذ `login-rate-limit-and-audit.sql`: أي حساب لجنة أو أدمن فرعي يُقفل تلقائياً 15 دقيقة بعد 5 محاولات دخول فاشلة متتالية، وتُسجَّل كل محاولة (ناجحة/فاشلة/مقفلة) في سجل النشاط.

## تجهيز المسابقة

1. أضف المتسابقين يدويًا أو استورد ملف Excel متعدد الشيتات. اسم المركز يُقرأ حصرًا من عمود "المركز" داخل كل صف — اسم الشيت نفسه لا يُستخدم كمركز إطلاقًا مهما كان. أي صف بلا عمود مركز أو بقيمة فارغة يُستورد ويُعلَّم بوضوح في القائمة والملخص بدل تخمين اسم مركز له. إعادة استيراد نفس الملف بعد تصحيحه لا تُكرّر المتسابقين: أي صف برقم جلوس يطابق متسابقاً موجوداً يُحدَّث (الاسم، المركز، الجنس...) من الملف مباشرة بدل إضافته من جديد، دون المساس بعلامته أو سحبه القائمين.
2. حدّد مستوى المتسابق من تسعة مستويات ثابتة (`LEVEL_CATALOG` في app.js)، وأرقام الأجزاء المشاركة فعلياً.
3. عند الاستيراد يمكن شمل أو استبعاد مستوى القرآن الكامل والروايات الأخرى.
4. "سحب للجميع" ينفّذ السحب لكل من أجزاؤه مسجَّلة، ويتخطى الباقي مع تقرير واضح بمن يحتاج تعبئة أجزائه.
5. نزّل نسخة JSON احتياطية دوريًا (في الوضع المحلي)، وجرّب استعادتها قبل يوم المسابقة.

## السحب والمواضع

- الموضع نصف صفحة من مصحف المدينة: 8 أسطر بالضبط، يبدأ وينتهي عند حدود آيات صحيحة.
- يُولَّد البنك بأسلوب النافذة المنزلقة لتقليل التكرار وتجنّب افتتاحات غير طبيعية قريبة من أول السورة.
- السحب عملية ذرية بالخادم (RPC واحدة) — لا يمكن للجنتين سحب الطالب نفسه بالتزامن.
- "إعادة موضع بسبب" لا يمكن أن يعطي نفس الموضع الحالي أو أي موضع سبق أن أُعطي لهذا الطالب من قبل بهذا السحب.
- رئيس/عضو اللجنة لا يقدران على بدء اختبار طالب جديد وعندهما طالب آخر "قيد الاختبار" لم يُنهَ بعد.

## التقييم الإلكتروني

| نوع الخطأ | الخصم |
|---|---|
| خطأ الحفظ | علامتان |
| خطأ اللغة | علامتان |
| خطأ التجويد | علامة واحدة |
| التردد | 0.2 لكل مرة |
| تغيير الموضع | 10 علامات |

العلامة من 100 ولا تقل عن صفر، والنجاح من 75 فأعلى. عند اختلاف رصد الرئيس عن العضو، يظهر جدول مقارنة لكل موضع مختلَف فيه فقط، ويدخل الرئيس عدد الأخطاء **المعتمد** (لا الخصم نفسه) لكل نوع مختلَف، والنظام يحسب الخصم تلقائياً.

## التسجيل اليدوي الطارئ (DR)

مسار منفصل تماماً عن التقييم الإلكتروني، لاستخدامه فقط عند تعطّل النظام أثناء الاختبار: تطلب اللجنة تسجيل علامة يدوية بسبب موضّح، ويعتمدها المدير أو يرفضها من الإعدادات.

## الاختبارات الآلية

تغطي الحسابات الأكثر حساسية (العلامة النهائية، الخصومات، مطابقة المستوى) — تُشغَّل يدوياً عبر Node بلا أي تبعيات خارجية:

```bash
node tests/scoring.test.js
node tests/level-catalog.test.js
```

شغّلهما بعد أي تعديل على منطق التقييم أو الاستيراد قبل رفع التغيير.

## بنية المشروع

```
index.html              كل الشاشات (بوابة الدخول، الإعداد، لوحة الإدارة، واجهة اللجنة)
app.js                  كل منطق الواجهة: المتسابقون، السحب، التقييم، التصدير
cloud.js                طبقة الاتصال بـ Supabase (تسجيل الدخول، المزامنة، RPC)
styles.css              نظام التصميم الكامل (متغيرات CSS + استجابة لكل الأحجام)
supabase/                ملفات SQL بترتيب التنفيذ الموضّح أعلاه
tests/                   اختبارات آلية بدون تبعيات
data/quran.json (يُحمَّل عند الحاجة) نص القرآن وبيانات الأسطر
assets/quran-pages/      604 صورة صفحة مصحف (لعرضها أثناء الرصد الإلكتروني فقط)
vendor/                  مكتبات خارجية مجمَّعة محلياً (لا CDN) لضمان العمل بلا اتصال
```
